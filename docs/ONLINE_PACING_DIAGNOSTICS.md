# Read-only online pacing diagnostics

Guarded recovery rendering is enabled by default. `TB_ONLINE_PACING=original` selects the original behavior for developer comparisons; `recovery-render` explicitly selects the default. Unset, empty and unknown values keep the default; unknown nonempty values log a diagnostic. The retired experimental selector, stale-phase/deadline probes and test-file control have no effect. Historical sections below describe old recordings only. Kind 16 retains its actual permitted-render meaning. Kind 19 is an opt-in guard snapshot on an original skipped render: `object` is the manager, `interval_bits` the queue, `local_sequence` the decoded remote frame, `previous_guest_us` the decoded local frame, `observed_guest_us` the current local frame, and `result_u32` the observation age in nanoseconds. Its `flags` bits 0–4 mean pending, unsupported, seen, invited and witnessed original frame advance. The guest-us names here are legacy shared JSON keys; these particular values are frame indices. Guard snapshots do not change guest state. Old trace kinds 14/15 remain readable by offline tools but are no longer emitted by the candidate.

The title executable includes `online_pacing.cpp`. `scripts/patch_online_pacing.py`, called by the existing network patcher during source and consumer configuration, attaches exact instruction hooks in `func_001A33CC`, `func_0016EEBC`, `func_0016DD64`, `func_0015B0BC`, `func_001D511C`, `func_0015361C` and the sendto/recvfrom import stubs. Separate lifecycle hooks reset the guarded helper's pending state. The patcher validates every required function and instruction before writing, tolerates game-free fixtures containing none, rejects partial or ambiguous title layouts, and is idempotent. It does not depend on generated chunk numbers or executable addresses. The existing runtime archive ABI stays unchanged; consumer packages carry the diagnostic source and its host clock header.

Set `TB_PACING_TRACE` to an output JSONL path and `TB_PACING_TRIGGER` to a trigger-file path before launching. Both are mandatory to create the writer. `TB_PACING_SECONDS` selects a 1–120-second window, default 20 seconds. `TB_PACING_ROLE=host` or `invited` labels the operator-selected role; otherwise the header says `unspecified`. The label does not infer role from a nonzero correction, since a client may have a zero correction. Start actual gameplay, then create the trigger file. Each process records at most one window. Restart for another window.

```sh
# Set these separately for each test process before launching it.
export TB_PACING_TRACE="$PWD/analysis/online-fps/step2/B-pacing.jsonl"
export TB_PACING_TRIGGER="$PWD/analysis/online-fps/step2/B-pacing.trigger"
export TB_PACING_ROLE=invited
export TB_PACING_SECONDS=20
# After verifying live gameplay:
touch "$TB_PACING_TRIGGER"
python scripts/pacing_report.py "$TB_PACING_TRACE"
```

With diagnostics disabled, each hook returns after checking the cached recorder state. Merely setting the path and trigger arms the recorder without collecting events; inactive-versus-active comparisons use the same binary. With diagnostics armed, a host worker polls the trigger every 10 ms. During recording, producers append numeric records to a preallocated 32,768-event buffer with a nonblocking mutex attempt. Full-buffer and contention drops are counted. The worker closes the window and writes the file after recording, keeping file I/O off the guest threads. Shutdown stops and joins the worker and flushes an interrupted window; storage remains alive during guest-thread teardown. An interrupted window has `complete: false` in its header and must not be used as a complete interval.

The JSONL header gives schema, role, requested host-time boundaries, completion status, capacity, dropped events and retained-event count. Event kinds are 1 (first pacing comparison while waiting), 2 (comparison allowing exit), 3 (completed correction write), 4 (sendto completion), 5 (recvfrom completion), 6 (received frame-snapshot subtraction), 7 (peak selection before decay), 8 (constructed numeric frame header), 9 (completed pacing-field reset), 10 (completed original network-clock calibration adjustment), 11 (original recovery request), 12 (decoded remote/local frame pair), 13 (title identity comparison), and 14 (experimental invalidation). Intermediate pacing polls are counted but not appended. Register and memory reads preserve the original floating-point deadline and comparison; the hooks do not recompute or replace the decision and do not write guest state.

Pacing records include the pacing-object address, previous guest timestamp, exact observed guest timestamp, current pacing interval float bits, raw unsigned correction, raw state flags, original floating deadline, original floating observed time and poll count. Correction-write records normalize the field address back to the pacing-object base. The field is unsigned in the pacing deadline. Received snapshot differences use signed 32-bit subtraction before positive values enter an unsigned peak calculation, described in [the arithmetic audit](ONLINE_FRAME_PACING.md). Raw flags are diagnostic state, not an automatic role classification.

All records carry local host monotonic nanoseconds from `tb_host_now`, the same clock domain used by the existing frame-budget and gameplay timing tools on that host. Frame-budget text timestamps subtract an origin; its startup log now records `[frame-budget] base_monotonic_ns=...` so the report can restore absolute timestamps exactly. Align events by these timestamps. For pacing events, `previous_guest_us`, `observed_guest_us`, `deadline_guest_us` and `observed_float_us` belong to the title-relative monotonic guest clock and must not be subtracted from host nanoseconds. Kinds 6–8 reuse numeric fields for network-clock operands, as specified below; those are a separate clock domain. Neither domain may be compared directly with another machine's local clock.

Socket records contain only local socket number, caller LR, raw return value, local call-start time and completion time. `local_sequence` is a monotonically increasing local completion number for that direction; `tx`/`rx` snapshot both local counters at append. Failed calls count too. These counters correlate correction writes and pacing decisions with local socket activity; they are not decoded wire sequence IDs, remote sender clocks or a direct RTT measurement. A recvfrom already blocked when recording starts has no captured call-start timestamp. The socket hooks do not read payloads. The separate title hooks read only the three numeric frame-header words described below, without copying payloads, credentials, account identifiers or remote addresses.

Use `scripts/pacing_report.py TRACE --json REPORT` to inspect correction values, guest deadline lateness, polls, local socket durations and time since the latest local receive completion. Temporal proximity does not establish which packet caused a correction. Dropped events invalidate claims that depend on a complete packet/correction timeline. Keep these traces separate from clean Step 1 baselines. The meaning and limits of the title's correction are recorded in [ONLINE_FRAME_PACING.md](ONLINE_FRAME_PACING.md).

To correlate a pacing trace with frame-budget flip intervals from the same process, pass `--frame-budget TRACE --startup-log LOG` to `scripts/pacing_report.py`. It requires exactly one logged frame-budget clock origin, adds that origin to the relative trace timestamps, and reports how many pacing/socket events overlap complete frame intervals. Older traces without the clock mapping are rejected for this correlation mode. The frame trace must actually overlap the pacing window.

## Producer and reset operands

These additional event kinds reuse the schema-1 numeric slots; inspect `kind` before interpreting them. All are read-only. The frame-header hook runs immediately after construction, not on arbitrary incoming bytes. It reads the frame index and two network-clock timestamps, without reading the account or gameplay payload.

| Kind | `object` | `local_sequence` | `previous_guest_us` | `observed_guest_us` | `correction_u32` |
| --- | --- | --- | --- | --- | --- |
| 6 | Synchronization queue | Matched frame index | Stored local frame snapshot | Remote frame snapshot | Raw wrapped remote-minus-local difference |
| 7 | Synchronization queue | Unused | Retained peak | Pending received peak | Unsigned maximum before gating/halving |
| 8 | Constructed header buffer | Outgoing frame index | Main-update network-clock snapshot | Network clock at header construction | Unused |
| 9 | Pacing object | Unused | Updated previous-frame timestamp | Unused | Field value immediately after its reset |

For kind 9, `flags` packs pacing bytes `+0x122`, `+0x12c` and `+0x12d` at shifts 16, 8 and 0. It observes those bytes at the reset instruction, before any later instructions in that return path. Kind 7 precedes the clock-ready, 512 µs threshold and pacing-phase checks, so a peak record does not guarantee a later correction write. Pacing exit records (kind 2) describe the wait-loop exit decision; reset records (kind 9) also cover paths which skip that loop.

Run `python scripts/online_pacing_audit.py TRACE --phases PHASES.json --gameplay TIMING.jsonl --json REPORT.json` to check retained deadline arithmetic, received subtraction, maximum selection, correction halving and zero-valued resets. `PHASES.json` is a list of local host-monotonic `start_ns`/`end_ns` intervals with labels; gameplay timing is optional. The default rejects interrupted or lossy recordings. `--allow-dropped` permits retained-event arithmetic and summaries with `lossless: false`; it never establishes a complete producer/reset timeline. The offline model in `scripts/online_pacing_model.py` is an analysis tool and is not linked into the game.

## Clock-calibration observations

Set `TB_PACING_CLOCK_ONLY=1` to filter recording to kind 10, keeping menu/pacing/socket activity from filling the bounded buffer before a peer joins. Arm the usual trigger immediately before the join or reconnect of interest. This is still a single bounded recording per process, and it can expire before an exchange starts. Inspect the event count and exchange completeness rather than treating an empty recording as a successful clock check.

Kind 10 runs immediately after the title's original 64-bit epoch write. `object` identifies its transport object, `socket` holds the network-manager guest address for this event kind, `local_sequence` is the title's calibration sample count, `previous_guest_us` is the old 64-bit RTC epoch, `observed_guest_us` is local RTC minus that epoch, `interval_bits` holds the remote response stamp, `result_u32` holds elapsed local time since the echoed request stamp, and `correction_u32` is the original wrapped epoch adjustment. These slots are reused numeric operands, not an actual socket number, nominal interval or socket return code for kind 10. The hook records no packet body or account identifiers.

Run `python scripts/online_clock_report.py TRACE --json REPORT.json` to compare the captured adjustment with the original calculation and the latest-response midpoint/bounds. The report groups transport/manager pairs and separates new exchanges starting at sample one. `complete_ten_samples` is a per-exchange check; `lossless` and `usable_timeline` separately describe the recording. A partial exchange can report retained samples but cannot reconstruct an unknown earlier RTT sum. The tool is offline and is not a dependency of the game or the builder. These observations did not justify changing calibration as an FPS fix; see the Step 4 decision in [ONLINE_FRAME_PACING.md](ONLINE_FRAME_PACING.md).

## Frame correspondence and recovery

Kind 11 observes the receive-side recovery branch before any experiment runs: `local_sequence` is the received host frame, `previous_guest_us` is the local frame, and `correction_u32` is their wrapped difference. Kind 12 records the same frame pair after the local frame is loaded; `observed_guest_us` is the remote network-clock snapshot and `interval_bits` holds the local sampled network time. These fields are numeric operands rather than monotonic pacing times for these kinds.

Kind 13 records the title's identity comparison: `local_sequence` and `result_u32` hold the two numeric member IDs, `flags` indicates equality, and `lr` is its guest caller. These IDs establish whether the title's ownership comparison changes; they do not contain RPCN account names. Kind 14 is emitted only when the `stale-phase` developer experiment actually invalidates a tracked estimate. It records the recovery frame in `local_sequence`, local frame in `previous_guest_us`, invalidated source frame in `observed_guest_us`, old correction in `correction_u32`, and old pending/retained peaks in `interval_bits`/`result_u32`.

For two processes on the same host, match kind 8's outgoing frame to kind 12's incoming frame using `local_sequence`, then compare their local monotonic timestamps. Use the most recent preceding construction if a frame index repeats and report missing/duplicate matches explicitly. This measures header construction to decoding, including local scheduling, not a packet RTT. Do not subtract timestamps from different machines without an established clock mapping. Full traces can drop events through contention; retain `dropped` accounting in any conclusion.

Historical Step 4 behavior (retired): the recorder remained read-only. Experimental writes occurred in the separate `tb_pacing_experiment` entry point, require the exact `TB_EXPERIMENTAL_ONLINE_PACING=stale-phase` opt-in, and have separate kind-14 action records. With no opt-in, the experiment returns without altering guest state. Its design, fallback rules and acceptance limits are documented in [ONLINE_FRAME_PACING.md](ONLINE_FRAME_PACING.md).

## Exclusive frame-time accounting

Set `TB_PACING_FRAME_ONLY=1` for focused pacing/flip investigation. It retains pacing, recovery, numeric producer/header/frame-pair, and main-update events (kinds 1–3, 6–9, 11–18), and filters socket events before buffer locking. It changes only diagnostic recording; original and experimental guest behavior are unchanged. `TB_PACING_CLOCK_ONLY=1` remains a separate filter and should not be combined with frame-only mode. Restart for each one-shot window and inspect drops even with this filter.

`python scripts/pacing_report.py TRACE --frame-budget BUDGET --startup-log LOG --json REPORT` now includes `frame_accounting`: an absolute-clock timeline between consecutive FIFO flips, clipped to pacing-event coverage. Each frame divides exclusively into the first-wait-comparison-to-exit pacing span, main-thread semaphore wait, overlap, and remaining wall time. The parts sum to the frame interval. Remaining time includes work, preemption and other waits, so it is not CPU execution. Callback/vblank delays are reported separately by unique flip sequence and must not be added again. Pacer resets, correction/interval/flag observations and recovery actions are recorded per frame; they do not establish simulation update counts.

A report with `usable_timeline: false` supports retained observations only. Do not infer missing phases, exact state progression or a complete causal timeline from a lossy trace. Zero-correction frame groups mean that observed exit corrections are zero; an interval without an observed exit is excluded from that group.

## Historical Step 6 developer probes

The following retired values were historical causal investigation tools: `recovery-no-wait` bypasses one original deadline branch after a fresh client catch-up request; `recovery-render` permits one actual render when a fresh catch-up request is exactly one host frame ahead. Both require observed client identity and enabled pacing, expire the request after 50 ms, reset at the existing lifecycle hooks, and leave guest clocks and counters unchanged. Neither is a release default or validated synchronization correction. The render probe leaves recovery/phase memory intact and changes only the value used for one render-gate branch. The deadline probe did not improve FPS in its first on/off experiment.

The retired in-process reversal mechanism used `TB_EXPERIMENTAL_PACING_CONTROL` to name a test file containing exactly `1` followed by a newline to enable the selected probe; missing, malformed or other content keeps original behavior. Reads occur at most four times per second while qualifying probe requests occur. This file control is available only after explicitly selecting a developer probe. Keep any accepted fix independent of this test control.

Event kind 15 records an actual deadline bypass and closes the corresponding recorded pacing wait without inventing an ordinary exit. Kind 16 records an actual permitted recovery render. Kind 17 observes the original render-gate value before intervention, using `flags` for its skip byte and `object` for the pacing object. Kind 18 observes the main game-update call at guest `0x000E0DA8`, using `interval_bits` for the float delta passed to `func_0001F518` and `object` for its receiver. This is a particular update boundary, not a count of every subsystem update. Compare summed delta against local elapsed time and both peers before interpreting extra renders as correct simulation. Frame-only recording now also retains numeric producer/header/frame-pair events (6, 7, 8, 12) and kinds 15–18 for this investigation; it still filters socket events. Inspect drops before using a complete timeline.


## Adaptive interval diagnostics

Step 9 adds read-only kinds 20–22, retained in frame-only mode. Kind 20 is recorded after `func_0016D038` selects its active-entry maximum: `object` is the manager, `interval_bits` is the local measured frame-average float, `result_u32` is the previous requested-interval float, `correction_u32` is the adjustment-factor float, and `observed_float_us` holds the selected maximum in seconds. That last JSON name is a legacy shared key; the value is not microseconds. Kind 21 follows the producer call and records manager `+0x40` in `interval_bits`, including the invited path that receives the shared value rather than selecting it. Kind 22 records a visited timing entry: `object` is its address, `local_sequence` is its numeric member ID, `interval_bits` is its float interval and `flags` is its status byte at `+0x15`. These events do not contain usernames or packet payloads.

Pacing comparison kinds 1/2 additionally expose their configuration address in `socket` and the measured average at configuration `+0x00` as raw float bits in `result_u32`. Their existing `interval_bits` still represents the requested interval at `+0x04`. For these event kinds `socket` is an address, not a network socket. The new observations preserve registers, memory, original arithmetic and the opt-in recovery-render decision. Restart the one-shot recorder and require complete lossless coverage before using the events as a causal history.
